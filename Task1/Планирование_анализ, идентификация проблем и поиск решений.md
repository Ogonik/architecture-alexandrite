## Работы по исправлению проблем первого приоритета
Прежде всего мы проводим работы по купирования проблем первого приоритета, которые явно влияют на бизнес и получаемую компанией выручку.

> P3. (1) MES - монолит, который объективно не выдерживает текущих темпов роста нагрузки

Достаточно серьезная проблема, которую нельзя решить быстрыми и эффективными методами. Однако, исходя из текущей описанной функциональности приоложение процесс разделения монолита на микросервисы не должен быть сильно сложным, т.к. доменов мало - 1 или 2. Решение данной проблемы имеет среднесрочную перспективу, т.к. гораздо больше влияет на устойчивость развития ИТ-ландшафта компании, чем на ее текущее состояние.

Планируемые работы:
 - P3.J1. (Т3, П2) Проектирование разделения на микросервисы
 - P3.J2. (Т5, П3) Реализация микросервисов, допиливание монолита для возможности разделения обращений к различным его частям.
 - P3.J3. (Т5, П3) Параллельный ввод микросервисов и постепенное замещение существующих функций монолита

> P3.1 (1) вычислительно сложная работа MES по расчету моделей выполняется в одном приложении с бизнесовой частью.

Самая критичная проблема, которая сильно влияет на текущую деятельность компании, необходимо выполнять с высоким приоритетом

Планируемые работы (зависимы, сверху вниз):
- P3.1.J1 (Т4, П1) Выделение из монолита функциональности расчета моделей таким образом, чтобы она была максимально независима, но при этом являлась частью монолита; Вынесение функциональности расчета моделей в отдельный сервис; Параллельный запуск монолита и микросервиса, канареечный релиз; Полный переход на отдельный сервис расчета моделей 


> P3.2 (1) Множество пользовательских запросов к MES на статусы заказов роняют приложение

Вторая критичная проблема, которая сильно влияет на текущую деятельность компании, необходимо выполнять с высоким приоритетом. Однако, необходимо отметить, что это лечение симптомов, а не причин. В следующем блоке работ постараемся изменить бизнес-процесс.

Планируемые работы:
- P3.2.J1 (Т4, П1) Внедрение сервиса кеширования (выбор стратегии кеширование, проектирование, реализация, тестирование, пилот, релиз) 


> P3.3 (1) Процесс раздачи заданий для операторов провоцирует повышенную нагрузку на ИТ

Источник проблемы P3.2. Необходимо, совместно с продакт-менеджером, подготовить предложения по изменению бизнес-модели работы операторов таким образом, чтобы избежать высокочастотных запросов к backend сервису. Процесс потенциально долгий, поэтому не отменяет выполнения мер по проблеме P3.2

Планируемые работы:
- P3.3.J1 (Т5, П2) Изменение бизнес-процесса работы операторов с заказами(исследование, согласование с бизнесом, проектирование, реализация, тестирование, пилот, релиз) 

> Р8. (1) не понятно как пользователь узнает о статусе заказа

Исходя из текущей диаграммы C4 не понятно, как текущие пользователи-клиенты узнают о статусе заказа, необходимо выполнить работы по уточнению бизнес-процесса работы клиента с заказом и выполнить доработки систем для улучшения пользовательского опыта.

Планируемые работы:
- P3.8.J1 (Т5, П2) Улучшение клиентского опыта работы с заказом (проектирование, реализация, тестирование, релиз) 

## Работы по исправлению проблем второго приоритета
> P2. (2) Внешнее API не закрыто компонентами обеспечивающими безопасность

Проблема влияет на общую безопасность ИТ решений компании. Т.к. API создания заказов публичное, то достаточно высоки риски атак на публичную точку. Необходимо реализовать меры по защите публичного API. Работы не первого приоритета и больше влияют на долгосрочную стабильность ИТ-ландшафта 

Планируемые работы:
 - ~~P2.J1 (Т4, П2) улучшить аутентификацию~~
 - P2.J2 (Т3, П2) поставить WAF
 - P2.J3 (Т3, П2) обеспечить rate limiting
 - P2.J4 (Т1, П2) закупить облачную защиту от DDOS   

> Р9. (2) Большой объем ручного тестирования 

Поскольку компания достаточно стабильно развивается, то необходимо тратить усилия на общую автоматизацию рутинной деятельности для освобождения ресурсов на реализацию новой функциональности. Автоматизация тестирования, особенно при наличии желания и компетенций в команде - отличный кандидат на реализацию:

Планируемые работы:
- P9.J1 (Т5, П2) Разработка скриптов АТ-тестирования
- P9.J2 (Т2, П1) Внедрение ночных сборок
- P9.J3 (Т2, П2) Реализация pipeline'ов прогона автотестов при ночных сборках

> P5. (2) Не обеспечена наблюдаемость всех приложений

Одна из первоочередных проблем для решения, т.к. отсутствии наблюдаемости (логи, трейсы, мониторинг) не позволяет определить точку отсчета при реализации новой функциональности и внедрении изменений в архитектуре приложения.

Планируемые работы:
- P5.J1 (Т3, П2) Внедрение инфраструктурного мониторинга (параметры загрузки железа) 
- P5.J2 (Т2, П1) Внедрение технологического мониторинга (Application Performance Monitoring)
- P5.J3 (Т3, П2) Внедрение бизнес-мониторинга (Параметры исполнения бизнес процессов) 
- P5.J4 (Т4, П1) Внедрение общего централизованного логирования
- P5.J5 (Т4, П2) Внедрение трейсинга

> Р12. (2) Использование одной БД для CRM API и для Shop API

Не понятно наличие факта использования одной БД двумя сервисами. Провоцирует потенциальные конфликтные ситуации и лишние зависимости в цикле разработка-тестирование-релиз. Необходимо разделение БД на 2, по одной для каждого сервиса.

Планируемые работы:
- P12.J1 (Т5, П2) Разделение ShopDB на 2 части (проектирование, реализация, тестирование, релиз)

## Общий подход к реализации задач
ВАЖНО! 
Долгие и большие фичи типа АТ-тестирования, разделения MES, реинжиниринга бизнес-процессов должны запускаться вместе с 0-м приоритетом, чтобы постепенно продвигаться к поставленным целям.

Одновременно необходимо быстро купировать актуальные проблемы бизнеса и приоритетно внедрить кеширование, мониторинг для более быстрой реакции на инциденты.
